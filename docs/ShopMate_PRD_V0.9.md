## 2. 问题与用户

### 2.1 用户面临什么问题？

消费者购买商品时，通常需要寻找商品、理解参数、比较差异，最后做出选择。过程中可能遇到以下困难：

- **不知道如何表达需求：** 例如“适合通勤的耳机”，难以直接转换成具体参数。
- **商品比较成本高：** 需要反复打开详情页、评测文章与参数表，才能看清两款商品的差异。
- **需求容易发生变化：** 修改预算或功能要求后，需要重新筛选。
- **推荐理由难以查证：** 参数表能确认是否支持 ANC，却回答不了实际降噪效果如何。
- **购物过程不连续：** 已经在浏览某个商品，却需要向独立 AI 工具重新说明购买背景。

以上是问题假设，通过用户研究验证（见 9.2）。

### 2.2 目标用户

**核心目标用户：已有明确购买意图，但难以把生活需求转换成筛选条件的消费者。**

**次要目标用户：** 已有预算和候选商品，希望减少反复搜索与比较的消费者。

两类用户的共同目标是选到合适的商品，而不是与 AI 聊得越久越好。ShopMate 应帮助用户缩小选择范围，不增加不必要的步骤。

### 2.3 典型使用场景

以下是**目标体验示例**，不代表当前版本已稳定通过完整流程。用户每天坐地铁上班，想买一副 300 元以内的蓝牙耳机，但不清楚降噪参数。

1. 在耳机列表页打开 ShopMate，输入“地铁通勤用，300 以内”。
2. 助手把预算设为硬约束，并建议加上“主动降噪”；用户确认。
3. 助手展示两款符合条件的耳机及关键差异。
4. 用户追问“哪款在地铁里降噪更好”，得到简短结论和来源。
5. 用户把预算改为 200 元，降噪要求保持不变，候选随之更新。

## 4. 产品方案与 MVP 范围

### 4.1 产品定位

**ShopMate 是嵌入电商购物场景的 AI 交互式选购助手。**

它不替代电商平台，也不负责交易，只在用户寻找商品、比较候选和修改购买要求时提供辅助。

第一版通过自建模拟电商 Web App 展示，不声称已接入淘宝、京东或其他真实电商平台。

### 4.2 核心用户流程

**打开助手 → 继承购物上下文 → 展示快捷选项或候选 → 必要时澄清需求 → 快速比较参数 → 按需展开证据 → 调整条件或完成选择。**

信息足够时先展示候选；只有缺少重要信息或存在条件冲突时才追问。**RAG 只用于需要外部资料支持的问题，不是每次筛选都触发。**

### 4.3 MVP 范围

产品定位面向多品类，首轮只做蓝牙耳机，以便在有限时间内完整验证用户体验与证据能力。

| 项目 | 第一版要求 |
| --- | --- |
| 使用入口 | 模拟购物首页、耳机列表页、耳机详情页 |
| 商品覆盖 | 蓝牙耳机 10–15 款；沙发为 P1 |
| 交互方式 | 快捷选项、文字输入 |
| 推荐 | 程序过滤硬约束后，展示 1–3 款候选 |
| 快速比较 | 同一屏幕查看两款商品的关键差异 |
| 证据问答 | 追问使用体验时，检索与型号对应的资料并给出来源 |
| 数据 | 核实过的商品快照 + 与型号绑定的证据资料 |
| 访问方式 | 手机优先的响应式 Web App，不接入真实交易 |

不支持的品类需如实提示，不由模型编造商品。

### 4.4 功能优先级

| 优先级 | 功能与边界 |
| --- | --- |
| **P0：完整选购闭环** | 带筛选与比较能力的模拟购物页面、AI 助手入口、页面上下文继承、快捷选项和文字输入、硬/软条件管理、结构化筛选、两款商品比较、按需证据问答与来源展示、手动同步到商品列表、异常处理及核心评测 |
| **P1：扩展能力** | 关闭期间列表条件发生变化时的专门冲突处理、复杂会话恢复、沙发品类、语音转文字、用户反馈与会话内排序优化、扩大商品及证据覆盖 |
| **暂不做** | 账号与交易系统、全网实时比价、长期用户画像、自动下单、连续实时语音通话、多 Agent 自主规划、Kafka/Flink 流处理 |

**P0 验收必须走通完整流程：** 用户在模拟商品页面打开助手 → 沿用当前页面条件 → 修改需求 → 查看符合硬约束的候选与两款比较 → 按需查看有来源的商品证据 → 将可映射条件应用回列表或返回商品详情。普通列表页同时作为 H0 用户对照实验的基线，不是次要功能。

开发时可以先分别调通前端、商品筛选和证据服务，但不能以某个单独模块可运行代替完整产品验收。

## 5. 交互设计

### 5.1 入口与首屏

| 进入场景 | 系统已知信息 | 打开后的表现 |
| --- | --- | --- |
| 购物首页 | 无品类或条件 | 展示品类入口，标明当前只能完整体验耳机 |
| 耳机列表页 | 品类，可能有筛选条件 | 继承已有条件，展示 1–3 款候选和 2–4 个快捷选项 |
| 耳机详情页 | 当前商品 ID 和参数 | 提供找相似款、比较商品、查看评测依据 |
| 关闭后再打开 | 当前会话已确认的条件 | 保留本次有效条件；需要显示结果时重新确认候选仍满足当前条件。更复杂的数据版本恢复逻辑为 P1 |

首屏原则：

- 只有商品类别时，可以展示基础候选，但要说明依据，不声称“最适合你”或未经证实的“最热门”。
- 快捷选项每轮 2–4 个，非必要问题可以跳过。
- 存在影响推荐的硬约束冲突时，必须先确认，不能擅自采用其中一组。
- 可以使用购物上下文，但不能仅凭用户浏览过某商品就认定用户喜欢它。
- 新回复到达时，底部阅读自动跟随；用户主动向上阅读时不强制跳转，并提供返回最新消息的入口。

### 5.2 用户怎样表达需求？

快捷选项和文字输入共用同一份购买条件。

例如：

- 先选择“300 元以内”，再输入“必须有 ANC”：保留预算，新增 ANC 硬约束。
- 再输入“预算改为 200 元，其他要求不变”：只更新预算，不删除 ANC 要求。
- 只说“这款降噪更好吗”，但无法确认“这款”指哪件商品：先澄清，不擅自猜测。

条件如何判定和更新，见 6.2 与 7.3。

### 5.3 助手与商品列表的同步

MVP 采用**手动确认同步**：助手内修改仅更新助手推荐；用户点击“应用到商品列表”后，才写回列表所支持的筛选条件。这样可能避免误改列表，但会增加一次操作，其价值通过 H2 验证。

| 场景 | 处理方式 | 优先级 |
| --- | --- | --- |
| A：从列表页打开助手 | 继承并展示列表的筛选条件 | P0 |
| B：在助手内修改条件 | 助手重新推荐，列表保持原状；点击“应用到商品列表”才同步；页面无法执行的重要条件须说明，普通场景和偏好不重复提示技术限制 | P0 |
| C：关闭期间列表条件变化 | P0 不自动以另一组条件覆盖现有状态；专门的差异比较与冲突选择界面在 P1 实现 | P1 |
| D：切换到未支持的品类 | 提示当前能力范围，不沿用耳机的条件和推荐结果 | P0 |
| E：开始新选购 | 清空助手的条件和推荐，不清除列表自身的筛选 | P0 |

### 5.4 推荐卡片与快速比较

用户的主要任务是**看懂候选商品的差异，而不是阅读整段 AI 报告**。

- **推荐卡片：** 商品图片、品牌型号、参考价格、2–3 个关键参数、简短推荐理由与核验日期。一次展示 1–3 款合格候选，不凑满数量；理由应说明已知差异，不套用相同文案。
- **快速比较：** 选中两款后，先展示同维度差异，例如价格、ANC、续航及已知限制。客观参数与主观体验分开，首屏不堆放长文。用户询问三款差异时，文字回答应覆盖所问商品，并说明并排表格仅支持两款。
- **展开证据：** 点击“为什么这样说？”“查看降噪依据”等入口，再加载与该型号相关的资料摘要，展示来源、日期和来源类别。
- **结果更新：** 条件修改后重新筛选，旧比较标记为过期；迟到的旧结果不能覆盖新结果。应说明符合条件的总数与当前展示数，不声称排序考虑了未实际生效的偏好。
- **完成选择：** 可以查看详情、返回列表或继续比较；不提供付款与下单。

### 5.5 商品证据问答

以下问题需要资料支撑：

- “这款耳机在地铁里的降噪有什么不足？”
- “长期佩戴会不会不舒服？”
- “两款耳机的主要取舍是什么？”

系统先确认用户所指的商品型号，再检索与该型号关联的资料，回答格式为**简短结论 + 关键依据 + 来源入口 + 不确定性**。厂商宣传、第三方评测、个人评价分开标识；来源有冲突时说明差异，不拼凑出无法支持的结论。

结构化参数足以回答的问题，不调用 RAG。第一版 RAG 不改变商品排名，只用于解释候选、回答追问和支持比较。

## 6. 业务规则

### 6.1 不可违反的推荐规则

**规则一：必须满足全部硬约束。** 预算不超过 300 元时，301 元的商品不能被推荐；“200 元以上”是价格下限，不能错误执行成“200 元以内”。不支持的条件必须说明，不能反向执行。

**规则二：必需功能未知时，不算满足。** 用户要求 ANC，商品没有可核实的 ANC 资料，就不能作为合格候选。

**规则三：软偏好只根据已有证据排序。** 不把“舒服”“好看”等主观描述变成精确评分。

**规则四：不能编造商品事实。** 商品名称、型号、价格、参数和来源必须来自核实过的数据；任何发现的关键虚构事实都必须修复，不能用总体通过率抵消。

**规则五：区分不同程度的数据缺失。**

- 缺少图片：使用中性占位图。
- 缺少有效价格：不能声称符合预算。
- 缺少必需规格：不能作为满足该条件的候选。
- 缺少非必要参数：显示“未知”。

**规则六：没有结果时不擅自放宽条件。** 可以说明原因并建议修改，由用户确认。

**规则七：出错后保留有效条件。** 允许重试，旧请求迟到的结果不能覆盖新结果。

**规则八：证据必须对应正确型号。** 每条片段带有商品 ID 或型号、出处和日期；相似型号不能混用；找不到资料时回答“证据不足”。

**规则九：引用不等于事实。** 区分厂商宣传、第三方测试与个人体验；资料有冲突时说明适用条件或不确定性。

### 6.2 硬约束与软偏好的判定

购买条件分为四类：**硬约束**（必须满足）、**软偏好**（影响排序）、**使用场景**、**待确认**。

| 用户说法 | 处理方式 |
| --- | --- |
| “300 以内”“不超过 300” | 硬约束：价格 ≤ 300 元 |
| “200 元以上”“至少 200 元” | 价格下限 ≥ 200 元；若当前筛选器不支持，说明限制，不执行成上限 |
| “必须有降噪”“不要入耳式” | 硬约束 |
| “300 左右” | 软偏好：接近 300 元的商品优先；超出的商品标明超出金额 |
| “最好有降噪”“轻一点” | 软偏好 |
| “地铁通勤用” | 使用场景：不直接变成约束；系统可以建议相关条件（如 ANC），标为“建议”，用户确认后才生效 |
| 无法判断 | 标为待确认并展示给用户，不擅自归类 |

### 6.3 商品数据与证据要求

第一版使用两类数据，均需与商品 ID 和准确型号对应。

1. **结构化商品数据：** 品牌、型号、价格及核验时间、ANC 等必需字段、官方规格链接，用于硬约束过滤和直接比较。
2. **证据资料：** 产品说明、专业评测中的短摘录与链接、必要的测试条件和个人评价标识，用于回答使用体验与取舍问题。

每条证据至少包含：`product_id / model`、来源链接、资料日期（不明则标注）、来源类别、原文位置。

**首轮数据规模：**

| 项目 | 规模 |
| --- | --- |
| 耳机 | 10–15 款，价格约 150–500 元 |
| 相似型号 | 至少 2 组同系列的不同版本，用于测试规则八 |
| 证据 | 每款计划整理约 3–5 条短证据，优先覆盖有来源且能回答问题的资料；不为凑数量虚构评论 |

其他要求：

- 价格是快照，不保证实时可售；过期价格不能作为符合预算的依据。
- 模拟数据与核实数据严格分开。
- 评测内容只保存短摘录和原始链接，不复制全文。来源类别、测试条件与观点的主观性需清楚标识。

## 7. AI 方案

### 7.1 AI 与程序的分工

ShopMate 采用**受控的 LLM 工具调用流程**，不要求复杂自主规划。LLM 理解自然语言和组织解释，程序维护真实条件状态并保证业务规则。

| 工作 | 负责模块 |
| --- | --- |
| 理解需求、识别歧义与必要澄清 | LLM + 确认交互 |
| 处理快捷选项、保存及合并条件 | 程序 |
| 查询商品、检查预算与必要规格 | 结构化检索和规则服务 |
| 为指定型号取回产品资料与证据 | 证据服务（按需检索） |
| 组织商品比较与证据解释 | 程序负责参数对比；LLM 负责基于证据的文字说明 |
| 校验商品 ID、型号、价格与硬约束 | 程序校验 |
| 判断主观结论是否忠实于来源 | 基于人工标注的样本评测与人工抽查；辅助自动判分不能替代人工核对 |
| 展示商品卡片、比较结果和来源链接 | Web 前端 |

### 7.2 主要工具

| 工具 | 作用 | 关键边界 |
| --- | --- | --- |
| `update_conditions` | 提取用户对条件的新增、修改、删除意图 | 程序验证变更并应用，模糊时先确认 |
| `search_products` | 先过滤硬约束，再依据有证据的偏好排序 | 不可放宽硬约束 |
| `compare_products` | 返回两款同品类商品的可核实参数差异 | 字段与型号必须一致 |
| `retrieve_evidence` | 为确定商品 ID 取回评测、说明书等证据 | 先绑定正确型号，缺证据时不能编造 |

快捷选项、直接参数比较等明确操作尽量由程序执行，不必每次调用 LLM。完整 API 与异常格式放在《技术与数据设计》。

### 7.3 条件更新机制

LLM **只输出需要变更的字段**，不重新生成完整条件；程序将合法变更合并到当前状态。

```text
当前条件：预算 ≤ 300 元，必须 ANC，场景：地铁通勤
用户输入：“预算改为 200 元，其他不变”
LLM 提议：修改 预算上限 = 200
程序合并：预算 ≤ 200 元，必须 ANC，场景：地铁通勤
```

- 支持新增、修改、删除和待确认的变更类型；未提及字段默认不变。
- 不能确定“这款”指哪件商品、或“300 左右”是否是硬预算时，先向用户确认，不擅自变更。
- 程序校验合法性、字段类型及冲突；用户可以撤销变更。
- 模型仍可能解析错误，因此需专门测试条件变更解析及多轮状态保持，而不是仅凭增量机制宣称零错误。

### 7.4 商品证据策略与 RAG 的使用边界

**第一版目标是证据增强的商品解释，而不是采用某个固定检索算法。** 对用户选中的商品，先通过准确 `product_id` 筛选证据；只有商品说明、独立测评等资料能支持的结论才可回答。

首轮优先保证证据与型号一致、引用可追溯。已接入的方案使用**按商品 ID 检索 + 官网 HTML 结构化切分 + 向量检索**；多商品比较时分别检索各款资料，再合并去重。证据只用于解释，不直接修改筛选和排序。

选型参考普通切分、结构化切分和混合检索的对照结果，暂不默认引入 BM25 + RRF。资料不足、来源冲突或型号不清时说明限制；说明书 PDF 与第三方评测仍待补充。检索命中不等于最终回答可靠，必须检查证据是否被正确使用。

### 7.5 性能与成本

- 点击快捷选项后优先更新结构化筛选结果，不无故等待 LLM。
- 参数比较先展示；展开证据时显示明确加载状态，不阻塞已经核实的商品信息。
- 记录各类操作的端到端响应时间（中位数、P90）、失败率、LLM 调用次数与 token 用量，必要时计算单次任务成本。
- **具体时延和成本目标在有真实运行数据后制定**，本版不预设 1 秒、3 秒或 8 秒的通过门槛。

### 7.6 技术选型

当前原型采用 Next.js + TypeScript、FastAPI 和 Gemini 工具调用；证据层使用 Gemini Embedding 与 FAISS。技术组件的采用以商品问答表现和运行成本为依据，不以检索指标单独判断产品效果。

## 8. 评测与指标

### 8.1 功能测试范围

规划 42 个围绕耳机完整选购流程的 P0 测试场景：

| 场景类别 | 数量 |
| --- | ---: |
| 单轮需求理解与筛选 | 6 |
| 多轮条件修改 | 6 |
| 无匹配商品与硬约束冲突 | 4 |
| 商品数据缺失及异步异常 | 4 |
| 购物上下文与页面同步 | 4 |
| 快捷选项与两款商品比较 | 4 |
| 证据取回与型号、来源匹配 | 6 |
| 证据回答、冲突与引用核查 | 6 |
| 无法回答与错误回退 | 2 |
| **合计** | **42** |

每例记录输入、预期、实际结果、数据与模型版本、失败原因和复测结论。必须区分模拟页面测试和真实 LLM/证据问答测试。

### 8.2 验收规则：关键错误一票否决

以下被列为**关键用例**；任何一项失败，当前版本均不满足 MVP 验收，即使 42 例的总体通过率已经超过 85%。

1. **硬约束失守：** 例如把超预算、缺失必要功能或必需规格未知的商品标记为合格推荐。
2. **商品身份错误：** 把相似型号混作同款，或把 A 型号的证据引用给 B 型号。
3. **虚构关键商品事实：** 编造不存在的商品、价格、规格、资料来源或无证据的关键性能结论。
4. **无证据时仍给确定结论：** 缺资料或资料冲突时不说明，而直接宣称商品性能优劣。
5. **状态破坏：** 用户仅修改预算，却悄悄删除或改变其他已确认硬约束；旧请求结果覆盖新条件。

关键用例需要全部通过并复测记录。**另外**，全部 42 个 P0 场景的总体通过率目标为 ≥85%（至少 36/42）。两个要求同时满足才达到初步验收目标；失败不能被平均指标掩盖。

### 8.3 商品证据与 RAG 评测

准备约 20–30 条问题，覆盖**有证据、证据缺失、相似型号、两款比较、来源冲突**等情况。当前数据规模较小，先评测能否稳定完成以下任务：

- **证据覆盖：** 按商品 ID 取回全部证据后，是否具备回答所需的资料；双商品问题是否覆盖双方。
- **型号与引用：** 是否正确关联每句话所依据的商品型号、来源和原文片段。
- **回答忠实度：** 是否区分官方规格、独立测试和主观体验；无证据时能否说明不知道。
- **回答代价：** 记录资料长度、token 用量、延迟和错误情况。

**简单基线：** 对已确认商品 ID 直接取回所有有效短证据，不排序、交给 LLM。小规模语料中，先不使用 Hit@3 来证明复杂检索优越，因为每款仅 3–5 条证据时该指标区分力可能很弱。

若后续商品和资料量明显增加，再在同一语料、同一候选数量、分开的调参与最终测试集上比较 BM25、向量和混合检索；只有带来实际改进才保留。旧代码检索项目的 Hit@k 不等于 ShopMate 的成绩。

对体验、主观观点及引用支持程度，先由人工标注测试样本并进行复核；如使用 LLM 辅助评价，需先检查其与人工判断的一致性，不宣称自动判断能发现全部幻觉。

### 8.4 核心指标

| 指标 | 初步要求或记录方式 |
| --- | --- |
| 关键用例通过 | **100%；任一失败则整体不通过** |
| P0 场景通过率 | ≥85%（至少 36/42），且关键用例全部通过 |
| 硬约束遵循率 | 100%；超预算、缺失必需规格等均视为关键错误 |
| 商品卡片关键字段正确性 | 100%（由核实数据直接映射，实际仍需核对） |
| 条件变更解析正确率 | 目标 ≥90%，并记录错误类型 |
| 未提及的已确认条件被更改次数 | 目标 0；涉及硬约束时为关键失败 |
| 页面条件同步正确性 | 目标 100%；错误覆盖视为严重问题 |
| 生成回答的事实与证据支持 | 报告抽样支持率、错误类型及每项关键虚构事实；目标无关键虚构输出 |
| 证据不足处理与型号匹配 | 分别报告正确/适用数量，关键型号误配一票否决 |
| 响应时间与成本 | 记录中位数、P90、每次任务调用次数与 token 消耗 |

所有目标都是**计划值，非实测结果**。必须报告分子、分母、样本数量、数据版本及失败案例；无适用样本记 `N/A`。不能靠不推荐或全部拒答来获得好成绩。程序验证结构化数据和硬约束，文本中主观性能结论由证据评审覆盖，**不承诺所有生成错误都会被自动检测到**。

### 8.5 真实上线后的观察指标

MVP 没有真实商业流量，不对以下指标提供结果。若进入真实平台，可关注助手打开率、进入商品详情页比例、完成比较比例、条件修改次数、证据展开率及“证据不足”出现率；同时结合用户满意度和误导性推荐投诉。

### 8.6 当前验证进度（截至 2026-11-03）

## 9. 假设与验证计划

### 9.1 产品假设清单

| 假设 | 验证方法 | 主要观察结果 | 不成立怎么办 |
| --- | --- | --- | --- |
| **H0：模糊需求下 AI 比普通筛选更省力** | 对照 A：相同商品数据和相近任务，比较普通筛选页与 ShopMate | 操作/输入次数、完成率、耗时、重复澄清；期待操作负担减少且完成率不下降 | 收窄为“商品比较 + 证据问答”，不强推对话式选购 |
| **H1：条件透明、可编辑能减少误解** | 观察用户修改预算等操作；必要时让用户复述当前条件 | **条件修改错误次数、重复解释次数**为主要指标；复述正确率仅辅助判断可理解性 | 缩减常驻条件信息，只在变更时突出显示 |
| **H2：手动同步比自动同步更少出错** | 用可点击/纸面原型比较手动应用与自动同步可撤销 | 同步错误、误操作、用户困惑、额外步骤是否可接受 | 改为自动同步与撤销 |
| **H3：按需提供证据有助于理解取舍** | 对照 B：只有参数解释 vs 可展开证据 | 选择理由的准确性、来源理解、阅读与等待负担 | 将证据放到用户主动追问环节 |

H0 优先检查**AI 对哪些任务有用**，不要求 AI 在所有明确条件筛选中都更快。小样本的量化结果用于发现趋势与问题，不作为行业或商业效益的证明。

### 9.2 用户研究与对照实验

计划邀请约 5 位近期有购物经历或明确选购意图的用户。访谈先了解最近一次实际购物时的比较方式、困难和决策依据；原型试用时观察真实操作，不仅询问是否喜欢 AI。

- **对照 A（H0）：** 普通筛选/比较页与 ShopMate 使用相同商品快照、相近任务；尽量交替安排体验顺序。
- **对照 B（H3）：** 在相同候选与资料基础上，比较无证据展开和允许按需展开证据两种解释方式。
- **同步原型（H2）：** 不必开发两套完整系统；以交互原型比较手动应用与自动同步可撤销。

单独记录系统响应时间、用户决策时间与点击/输入次数。结果应包含失败样本、用户反馈与后续设计调整；约 5 人的定性测试不能用于宣称统计显著或真实转化率增长。

## 10. 开发计划与风险

### 10.1 开发顺序与完成标准

| 阶段 | 主要任务 | 可交付与验收重点 |
| --- | --- | --- |
| 1. 轻量竞品体验与需求准备 | 基于已有公开资料，只在 1–2 个可访问产品上完成少量任务；同时整理商品数据 | 《竞品分析报告》记录实际观察、截图与来源；不等待研究完所有平台 |
| 2. 购物页面与交互骨架 | 复用现有 UI，增加模拟耳机列表、基础筛选、商品详情、内嵌助手入口、快捷选项 | 普通筛选页可独立完成任务，并可作为 H0 对照 |
| 3. 结构化购物闭环 | 接入 LLM 的增量条件理解，完成程序过滤、条件保留、两款比较和页面条件同步 | 用户从列表打开助手，能够修改需求、查看候选并返回列表 |
| 4. 按需证据问答 | 整理准确型号的证据；先按商品 ID 取回全部有效短证据，再生成来源可查的解释 | 型号对应正确，证据缺失/冲突时正确说明，不因 RAG 阻塞基础参数比较 |
| 5. 评测与迭代 | 执行 42 个 P0 场景、证据/回答评测与少量用户试用 | 关键用例全部通过、一般功能达标，提供实际结果和失败修复记录 |
| 6. P1 决策 | 根据验证结果决定扩展沙发、语音、复杂状态恢复和更大资料库 | 只在确有需要时启动，不影响 P0 验收 |

商品资料整理可以与页面开发并行；后台服务也可先单独调试。**但 P0 的完成标准始终是用户从购物页面进入并走完一次端到端选购流程**，不能只有独立 Agent 或检索 Demo。

### 10.2 主要风险与取舍

| 风险 | 应对方式 |
| --- | --- |
| 普通筛选方式对明确需求已经足够好 | 用 H0 找到 AI 真正有价值的任务，而不是强行让所有操作使用 AI |
| 竞品已具备类似功能 | 借鉴成熟方案，不宣称独有优势；竞品实测记录放独立报告 |
| LLM 将软偏好误判为硬约束 | 展示条件分类、要求确认，并测试解析错误 |
| 购物页面与助手状态不一致 | P0 实现受控同步；复杂重开冲突场景放 P1 |
| 商品信息失效或价格不准 | 保存来源、核验日期和适用范围，过期快照不当作实时价格 |
| 相似型号混淆与证据矛盾 | 严格使用商品 ID，保留来源及测试条件，关键错配一票否决 |
| 只有少量证据，复杂检索收益有限 | 先使用商品 ID + 全量短证据的简单基线，按资料规模决定是否扩展检索 |
| 生成式回答不忠实于证据 | 结构化字段程序校验；主观结论用人工样本核查，发现关键虚构即修复 |
| RAG 增加响应等待和成本 | 参数结果先显示，证据按需展开，实测延迟与 token 开销 |
| 模型限流、超时或回复校验误拦 | 保留已生效条件，说明失败并允许重试；分别记录 API 错误与校验错误，避免有依据的回答被反复拒绝 |
| 跨商品比较证据不全或解释空泛 | 检查各商品证据是否齐全，并核对推荐理由是否回应当前偏好；不以召回提升代替购物任务达标 |
| 开发范围继续扩大 | P0 以完整选购闭环为边界，P1 不成为首轮完成的前提 |
| 样本有限 | 报告真实观察与限制，不夸大结论 |
